# Phase 0 tenancy integration foundation

This bundle runs the actual backend Docker image, native worker process, PostgreSQL 16, and actual frontend Docker image/Chromium. Only external providers are faked: real SMTP delivery goes to a synthetic mailbox; HTTPS model and MCP requests go to an isolated provider. It does not add testing routes, mock application authentication, use static API-token bypasses, or process turns from a test endpoint.

## Run locally

Requirements: Docker with Compose, Python 3.12+, Node/npm, OpenSSL, and Chromium installed by Playwright. Both application repositories must be checked out. The invoking repository supplies this harness; `pair.json` pins the counterpart to an exact Git revision. CI rejects dirty inputs and floating counterpart revisions.

```sh
cd /Users/sawarn/Downloads/weaves-app
npm ci
npx playwright install chromium
cd /Users/sawarn/Downloads/weaves
python3.12 -m tenancy_harness.run --backend ../weaves --frontend ../weaves-app --candidate backend --allow-dirty
```

`--allow-dirty` is for explicitly recorded local work only and is rejected in CI. From the frontend checkout, use its vendored bundle with `--candidate frontend`. The host orchestrator also requires Python 3.12+; CI pins Python 3.12, and application/fixtures run in Python 3.12 containers. Do not pass production URLs, env files, or credentials. The runner generates its own database identity, secrets, TLS certificate, ports and random project, uses only its explicit environment file, and rejects unsafe targets before mutation. No production configuration is read.

The default output is ignored `.local/tenancy/`. A unique project `weaves-tenancy-<12 hex>` owns all containers/networks and the temporary PostgreSQL data. Cleanup always removes that project's containers/data on normal success/failure; it cannot name `weaves-single`. If the host is forcibly terminated, remove only the exact project recorded for that run. No host PostgreSQL port is exposed. Data/provider services have an internal Docker network; only the frontend reverse proxy has a host-facing network and a loopback port.

## Fixtures and scope

Two normal organizations each have two workspaces, Admin/Builder/User personas, a shared-email human with different tenant roles, and a workspace-bound service account. Sentinel data covers identity/roles, provider/profile/secret, custom connector, agents/versions, workflows/versions, governance policy, private skill/version, private and workspace tasks, conversation/transcript and durable execution/audit records generated by the real worker. A third disposable organization exists exclusively to observe archived/suspended execution. The full ownership inventory also maps families whose deeper lifecycle tests arrive in later phases; seeded sentinels are not a claim that every API flow is exhaustively covered yet.

Every human fixture session is issued using real challenge/SMTP/verify endpoints. Synthetic distinct client addresses model independent people without disabling native IP throttles; the API trusts forwarded addresses only inside this isolated test stack, as a reverse-proxied deployment does. No production auth/session behavior is altered. The shared human remains separate tenant-local identities until Phase 3.

`ownership.json` maps every current repository collection and registered API operation. Backend contract tests fail if a collection/operation is added without classification. `TENANCY_ARCHITECTURE.md` in the backend records the target account/linking/private-content/lifecycle/migration decisions.

## Required cases and known issues

`pair.json` lists 11 required controls and five diagnostic IDs. The runner rejects missing, duplicate, skipped, failed, flaky or otherwise nonpassing required cases. Browser tests fail immediately without the private fixture and generated loopback URL. Authentication, foreign-ID/nested-reference denials, private skill/task audiences, role distinctions, service-key scope, real browser catalogs and native worker results are checked.

Diagnostics T0-D01–05 reproduce the five confirmed Phase 1 issues. They deliberately report `known_defects` separately and `saas_ready: false`. A changed observation fails the baseline so the corresponding control/ledger must be reviewed. Phase 1 converts each diagnostic into an isolation regression and removes it from the open ledger; no permanently skipped or expected-failing tests are introduced.

## CI and source pairing

Both deployment workflows require the new `tenancy` job as well as their existing verification job. Backend candidates use the pinned frontend revision; frontend candidates use the pinned backend revision. The backend job requires `TENANCY_FRONTEND_READ_TOKEN`, a fine-grained Actions secret with Contents: read limited to the private frontend repo. GitHub disables deploy keys on that repository, so no deploy key is used. A missing token fails the required job explicitly; it is never replaced with a personal login token or a skipped test. Frontend jobs can read the public backend. Fork PRs without access to the required private fixture must fail closed; do not use `pull_request_target` to run untrusted code with credentials.

The portable bundle is authored in `weaves/tenancy_harness` and vendored byte-for-byte into `weaves-app/tenancy_harness`. This allows both repos to test against existing pinned application revisions without a circular requirement that both new harness revisions ship simultaneously. Update it with:

```sh
python3 scripts/sync_tenancy_harness.py --frontend ../weaves-app
```

The content lock detects drift, missing files and stale copied code. Pin changes are explicit reviewed changes to `pair.json`; never substitute a floating `main`. CI reports actual source SHAs, dirty state, image content IDs, schema version, bundle digest and case outcomes. Existing lint/type/size/unit/browser/image checks stay in place. Legacy optional integration specs are separate; this required suite does not silently skip for missing endpoint variables.

## Credentials and artifacts

Only `artifacts/report.json` is suitable for upload. Private fixtures, mailbox codes, Compose env, ephemeral TLS key, browser output and any debugging logs stay under `private/` and are never uploaded. Playwright trace/video/screenshots are off for this suite because default network traces can contain bearer headers. The public report contains IDs/statuses and revision evidence, not request payloads, credentials or raw errors. Treat synthetic credentials as private nonetheless.

## Current limits

This is a Phase 0 foundation, not fixes for the five defects or implementation of global accounts, RLS, quota fairness, billing, SSO policy, all role permutations or load/recovery behavior. Later phases extend the same fixtures and required inventory. Production, cloud resources, real email/model charges, and production migrations are outside this harness.

## Opt-in live AI and lifetime testing budget

The ordinary required CI suite never calls a paid model. Live testing is explicit:

```sh
python3.12 -m tenancy_harness.run --backend ../weaves --frontend ../weaves-app --candidate backend --allow-dirty --live-anthropic-env /Users/sawarn/.config/weaves-testing/.env
```

The local env file supplies `WEAVES_TEST_PROVIDER=anthropic` and `WEAVES_TEST_API_KEY`; an optional `WEAVES_TEST_MODEL` overrides selection. The current smoke uses Haiku for one agent and Sonnet for a two-agent approval workflow, with three planned calls, 256 output tokens per call, a pinned org skill and synthetic read-only MCP context. Three additional Chromium cases check the actual transcript, browser approval/downstream execution, and cross-tenant denial. The live relay forwards the genuine Anthropic protocol to the fixed real API origin; model execution is real, while connector content stays synthetic and no external write tools are enabled. A separate `--canvas-probe` validates the browser flow with fake models and must pass without skipped cases.

The user's exhaustive **USD 100 lifetime cap** is stored outside both repos in `/Users/sawarn/.config/weaves-testing/budget.json` and `testing-spend.sqlite3`. The ledger is not initialized by a run and is never part of a disposable Docker volume. Missing ledgers, changed caps, unknown/stale prices, unsupported paid features, and insufficient funds block dispatch. Future runs/models share the same ledger; neither a new run nor a repository change creates a new allowance. An increase requires explicit user authorization.

Before every paid request, SQLite atomically reserves USD 1 and enforces the run's three-call maximum. This hold bounds the supported text request envelope (32 KB input payload; at most 256 output tokens; known models; no hosted tools, caching, streaming, premium inference parameters or image requests). Confirmed usage settles at the verified public rates with a 2x conservative accounting margin. Unknown/error outcomes keep their whole reservation; no free retry or automatic release is assumed. Prices must be reverified after 14 days. This is conservative usage accounting, not an Anthropic invoice; unrelated use of the same key outside this controlled harness is not visible here and must not be treated as free testing allowance.

Only the live provider relay receives outbound model access and the persistent budget mount. Ordinary API/worker containers remain on the internal network and cannot bypass it. Unit tests prove denial before network dispatch, concurrent cap enforcement, restart persistence, uncertain holds, and failure on missing/reset budgets. Tests do not increase or reset the real ledger. The public result includes a budget snapshot and verified usage/provenance, never the key or model response payloads.
