# Tenancy integration foundation and Phase 1 controls

This bundle runs the actual backend Docker image, native worker process, PostgreSQL 16, and actual frontend Docker image/Chromium. Only external providers are faked: Google sign-in goes to a fake OpenID Connect provider; HTTPS model and MCP requests go to an isolated provider. It does not add testing routes, mock application authentication, use static API-token bypasses, or process turns from a test endpoint.

## Run locally

Requirements: Docker with Compose, Python 3.12+, Node/npm, OpenSSL, and Chromium installed by Playwright. Both application repositories must be checked out. The invoking repository supplies this harness; `pair.json` pins the counterpart to an exact Git revision. CI rejects dirty inputs and floating counterpart revisions.

```sh
cd /Users/sawarn/Downloads/weaves-app
npm ci
npx playwright install chromium
cd /Users/sawarn/Downloads/weaves
python3.12 -m tenancy_harness.run --backend ../weaves --frontend ../weaves-app --candidate backend --allow-dirty
```

`--allow-dirty` is for explicitly recorded local work only and is rejected in CI. From the frontend checkout, use its vendored bundle with `--candidate frontend`. The host orchestrator also requires Python 3.12+; CI pins Python 3.12, and application/fixtures run in Python 3.12 containers. Do not pass production URLs, env files, or credentials. The runner generates its own database identity, secrets, TLS certificate, ports and random project, uses only its explicit environment file, and rejects unsafe targets before mutation. No production configuration is read.

The default output is ignored `.local/tenancy/`. A unique project `weaves-tenancy-<12 hex>` owns all containers/networks and the temporary PostgreSQL data. Cleanup always removes that project's containers/data on normal success/failure; it cannot name `weaves-single`. If the host is forcibly terminated, remove only the exact project recorded for that run. No host PostgreSQL port is exposed. Data/provider services have an internal Docker network; only the frontend reverse proxy has a host-facing network and a loopback port.

## Fixtures and scope

Two normal organizations each have two workspaces, Admin/Builder/User personas, a shared-email human with different tenant roles, and a workspace-bound service account. Sentinel data covers identity/roles, provider/profile/secret, custom connector, agents/versions, workflows/versions, private skill/version, private and workspace tasks, conversation/transcript and durable execution/audit records generated by the real worker. A third disposable organization exists exclusively to observe archived/suspended execution. The full ownership inventory also maps families whose deeper lifecycle tests arrive in later phases; seeded sentinels are not a claim that every API flow is exhaustively covered yet.

The harness is account-only and signs in only through Google, the product's one sign-in method. It never uses a password, email code, invitation, onboarding, legacy browser-cookie or tenant-SSO sign-in.

### Fake Slack server (opt-in, no real Slack)

`fake_slack.py` (state in `fake_slack_state.py`, Web API methods in `fake_slack_methods.py`, delivery timing in `fake_slack_delivery.py`) is served by the `provider` fake under `/slack` and is inert unless a test calls it. It uses a made-up signing secret (`TENANCY_SLACK_SIGNING_SECRET`) and made-up tokens, contacts no real host, and adds no required control. `POST /slack/api/{method}` models `oauth.v2.access`, `auth.test|revoke`, `chat.postMessage|update|delete|postEphemeral`, `reactions.add`, `assistant.threads.setStatus`, `conversations.replies` (one request per minute per workspace, 15 messages) and `conversations.list`; `POST /slack/response/{id}` is a `response_url` receiver (5 uses in 30 minutes). `/slack/_control/` has `deliver_event`, `deliver_interaction` (signed, form-encoded), `calls`, `state`, `configure` (fault injection: `api_fault` 500, 429 or slow, `delivery_fault` bad_signature or stale_timestamp, `status_mode`, `retry_schedule_seconds`) and `reset`. Delivery counts a response as an ack only if it is 2xx within 3 seconds, retries per the schedule (test default `[0,1,5]`, real `[0,60,300]`) with `x-slack-retry-num` and `-reason`, honors `x-slack-no-retry`, and reports whether a `url_verification` challenge was echoed. Control `T7-S00` (`phase7/slack_selftest.py`) is listed as planned in `phase7/__init__.py` (not in `pair.json`, whose `planned_controls` the beta gate requires to stay empty) until a later slice requires it.

### Harness signs in through a fake Google provider

The `provider` fake (`fake_google.py`) serves a discovery document, a JWKS (RSA key with a `kid`, `use=sig`), an authorize endpoint and a token endpoint. The token endpoint validates `grant_type`, the code, `redirect_uri`, `client_id`, `client_secret` and the PKCE `code_verifier` against the stored challenge, and returns an RS256 ID token (`iss` = the discovery issuer, `aud`, a `sub` stable per email, `email`, `email_verified`, `name`, `nonce`, `iat`, `exp`). The API container reads discovery from the provider's plain-HTTP listener (`WEAVES_GOOGLE_DISCOVERY_URL`, port 8081, private network); its token and JWKS URLs are internal. Its `authorization_endpoint` is the harness reverse proxy, `<app origin>/fake-google/authorize`, the only provider path the browser can reach; `gateway.conf` proxies exactly that path.

The authorize endpoint has no consent screen. It picks the person from the `login_hint` query parameter, else from the control file `private/google/identity.json` (written by the host-side browser helper), and redirects straight back with `code` and `state`. `fake_unverified=1` (or `email_verified: false` in the file) issues an unverified-email token, and `fake_deny=1` (or `deny: true`) redirects with `error=access_denied`; the negative controls use these.

The app origin is `http://localhost:<random port>`, written per run into the Compose env file as `TEST_APP_ORIGIN` and used for `WEAVES_PUBLIC_FRONTEND_URL`, `CORS_ORIGINS` and the fake's redirect check. (`localhost`, not `127.0.0.1`, because the API refuses `Secure` cookie sessions on plain HTTP anywhere else.) `WEAVES_BROWSER_SESSION_SECRET`, the Google client ID/secret and the rest are generated per run; `WEAVES_ACCOUNT_ALLOWED_EMAIL_DOMAINS=tenancy.test,custom-claim.test` keeps the allowlist exercised; `WEAVES_PUBLIC_EMAIL_DOMAINS=tenancy.test` makes the fixture domain a public provider so tenants share it freely, while `custom-claim.test` is a custom domain used for the organization email-domain controls.

Fixtures (`client.py`) sign in over HTTP exactly as a browser does: `GET /account/google/start` without following redirects, `GET` the authorize URL with `login_hint` (on the provider's internal address), `GET /account/google/callback` with the `__Host-weaves_google_oauth` binding cookie, collect the `__Host-weaves_account_session` cookie, then `GET /account/browser/me` for the CSRF token. An actor is `{Cookie, X-Weaves-CSRF, Origin, X-Organization-Id, X-Workspace-ID}`; requests carry the app origin as `Host`. Each fixture organization is created by an owner through `POST /account/browser/organizations` with an `Idempotency-Key` (`WEAVES_ALLOW_ACCOUNT_ORGANIZATION_CREATION` is enabled in `compose.yml`). Builder, User and shared-person members are provisioned with the admin `POST /users` route and sign in through Google, which links their membership. Service accounts use their API credential as the bearer. Bearer account sessions cannot be minted over HTTP; the one control that needs one (T1-I09, identity removal) and the "creates nothing" checks use `operator.py`, which mirrors the operator break-glass script against the disposable database.

Browser controls sign in through the real redirect flow. `browser_account.cjs` is the only module that knows the frontend's sign-in UI: `openAsAccount(page, tenant, {actor, route})` writes the identity file, navigates to `/api/v0/account/google/start?return_to=...` (the backend redirects through the proxied fake and back with the cookie set), and then uses the application's own organization chooser. The frontend must keep no token in storage; the helper asserts that and checks the cookie's `HttpOnly`/`Secure`/`SameSite=Strict`. Selectors the onboarding frontend may rename are isolated in its `SELECTORS` table and marked `TODO(frontend-onboarding)`. Synthetic client addresses are no longer needed: the code-throttle they modelled was removed with email codes. No production auth/session behavior is altered. The shared human is one account with a membership in each organization.

For local debugging only, `run.py --api-only` omits the controls that need the signed-in frontend (T0-I10, T1-I05, T1-I10 and the browser part of T1-I01). It never writes a passing report and is refused when `CI` is set or with live testing.

`ownership.json` maps every current repository collection and registered API operation. Backend contract tests fail if a collection/operation is added without classification. `TENANCY_ARCHITECTURE.md` in the backend records the target account/linking/private-content/lifecycle/migration decisions.

### Organization lifecycle control (T4-I02)

`lifecycle_checks.py` runs after the native worker starts (`WEAVES_LIFECYCLE_POLL_SECONDS=1` in the Compose runtime) and records `organization_lifecycle` in the private fixture file. Two disposable accounts create organizations through the account API. The owner exports (attachment, `no-store`, no other tenant), types the wrong then the exact name to request deletion, sees only the narrow allow-list, and cancels. The operator then runs the real `infra/gcp/singlevm/organization_lifecycle.py` (mounted into the seed container) with the database owner connection: `suspend` gives the identical `403 Organization not available` for the owner while the creator's other organization still works, the owner cannot cancel or resume, and `resume` restores it. Deletion is requested by the owner, grace is skipped with `purge-now --confirm-organization-name` (wrong name refused), and the independent worker purges: only the retained lifecycle and audit rows remain, secrets are gone, the other organization is unchanged and the deleted one is refused forever. A second organization is deleted afterwards (the worker keeps running), and a deleted organization still counts toward the per-account creation cap. No browser is used.

## CI and source pairing

Both deployment workflows require the new `tenancy` job as well as their existing verification job. Backend candidates use the pinned frontend revision; frontend candidates use the pinned backend revision. The backend job requires `TENANCY_FRONTEND_READ_TOKEN`, a fine-grained Actions secret with Contents: read limited to the private frontend repo. GitHub disables deploy keys on that repository, so no deploy key is used. A missing token fails the required job explicitly; it is never replaced with a personal login token or a skipped test. Frontend jobs can read the public backend. Fork PRs without access to the required private fixture must fail closed; do not use `pull_request_target` to run untrusted code with credentials.

The portable bundle is authored in `weaves/tenancy_harness` and vendored byte-for-byte into `weaves-app/tenancy_harness`. This allows both repos to test against existing pinned application revisions without a circular requirement that both new harness revisions ship simultaneously. Update it with:

```sh
python3 scripts/sync_tenancy_harness.py --frontend ../weaves-app
```

The content lock detects drift, missing files and stale copied code. Pin changes are explicit reviewed changes to `pair.json`; never substitute a floating `main`. CI reports actual source SHAs, dirty state, image content IDs, schema version, bundle digest and case outcomes. Existing lint/type/size/unit/browser/image checks stay in place. Legacy optional integration specs are separate; this required suite does not silently skip for missing endpoint variables.

## Current limits

The first Phase 1 containment infers legacy descriptor ownership from all installation references, retaining disabled references and rejecting orphans/conflicts before dispatch. Before activation, ambiguous references require operator resolution and cannot be removed through ordinary disconnects; after activation, scoped cleanup can remove those references while the descriptor remains quarantined. Explicit persisted ownership is implemented as an operator-activated migration 20, keeping descriptor JSON unchanged. Default startup remains at schema 19 until a compatible reader image has been deployed and activation is requested. The fixture activates 20 under a warm API, starts the native worker afterward, and requires T1-I02 to verify new owned connections, foreign-reference denial, and persistent quarantine after browser cleanup. Model egress is now the required T1-I03 control. Production, cloud resources, real email/model charges, and production migrations are outside this harness.

## Opt-in live AI and lifetime testing budget

The ordinary required CI suite never calls a paid model. Live testing is explicit:

```sh
python3.12 -m tenancy_harness.run --backend ../weaves --frontend ../weaves-app --candidate backend --allow-dirty --live-anthropic-env /Users/sawarn/.config/weaves-testing/.env
```

The local env file supplies `WEAVES_TEST_PROVIDER=anthropic` and `WEAVES_TEST_API_KEY`; an optional `WEAVES_TEST_MODEL` overrides selection. The current smoke uses Haiku for one agent and Sonnet for a two-agent approval workflow, with three planned calls, 1,024 output tokens per call, a pinned org skill and synthetic read-only MCP context. Three additional Chromium cases check the actual transcript, browser approval/downstream execution, and cross-tenant denial. Canonical hosted URLs resolve to the isolated TLS fake, with explicit fixture-only operator CIDRs. A private bridge forwards native Anthropic traffic to a separate budget relay; that relay alone joins the external network and forwards the genuine protocol to the fixed real API origin; model execution is real, while connector content stays synthetic and no external write tools are enabled. A separate `--canvas-probe` validates the browser flow with fake models and must pass without skipped cases.

The user's exhaustive **USD 100 lifetime cap** is stored outside both repos in `/Users/sawarn/.config/weaves-testing/budget.json` and `testing-spend.sqlite3`. The ledger is not initialized by a run and is never part of a disposable Docker volume. Missing ledgers, changed caps, unknown/stale prices, unsupported paid features, and insufficient funds block dispatch. Future runs/models share the same ledger; neither a new run nor a repository change creates a new allowance. An increase requires explicit user authorization.

Before every paid request, SQLite atomically reserves USD 1 and enforces the run's three-call maximum. This hold bounds the supported text request envelope (32 KB input payload; at most 1,024 output tokens; known models; no hosted tools, caching, streaming, premium inference parameters or image requests). Confirmed usage settles at the verified public rates with a 2x conservative accounting margin. Unknown/error outcomes keep their whole reservation; no free retry or automatic release is assumed. Prices must be reverified after 14 days. This is conservative usage accounting, not an Anthropic invoice; unrelated use of the same key outside this controlled harness is not visible here and must not be treated as free testing allowance.

Only the live provider relay receives outbound model access and the persistent budget mount. Ordinary API/worker containers remain on the internal network and cannot bypass it. Unit tests prove denial before network dispatch, concurrent cap enforcement, restart persistence, uncertain holds, and failure on missing/reset budgets. Tests do not increase or reset the real ledger. The public result includes a budget snapshot and verified usage/provenance, never the key or model response payloads.

The 1,024-token live ceiling leaves room for models whose default adaptive thinking consumes the output allowance before producing text. The existing USD 1 reservation still covers the worst permitted text envelope at the verified prices and conservative multiplier; the exhaustive lifetime cap stays USD 100. See [Anthropic Haiku 5.5 thinking guidance](https://platform.claude.com/docs/en/models/haiku-5-5/migration-guide). Empty model replies remain failures; task failure evidence is saved privately before cleanup, and the harness never retries paid calls automatically.

## T5-I05 request correlation, structured logs and internal metrics

`phase5/correlation_checks.py` runs in the seed container after the worker is up. Tenant A's admin creates a task with a caller-chosen `X-Request-Id` and a prompt sentinel. Durable rows must show the id on the persisted task turn and on the run's audit events (`correlation_id`), and on no other tenant's rows; malformed inbound ids (spaces, markup, too long or short) are replaced by a generated id. `GET /api/v0/internal/metrics` answers a direct peer with Prometheus text that contains no tenant identifiers, and answers 404 behind the gateway or with any `X-Forwarded-*` header. The host then reads the `api` and `worker` container logs (`phase5/correlation_logs.py`, stdlib only): every line is JSON, one API line and one worker line carry the request id with tenant A's organization, correlated lines never name tenant B, and neither the prompt sentinel nor any session credential appears anywhere in the stream. The probe (including the credentials to search for) is deleted from the fixture file after the check.

## T4-I03 schedule timezones

An extra organization (`zones`) is created through the real account API with `America/New_York`, so its seeded interval schedule inherits that zone. `schedule_timezones.py` also publishes two calendar workflows and then rewrites one calendar-settings payload and one interval-schedule payload with SQL to drop `timezone`, which reproduces what the previous release stored (legacy records). `schedule_timezones.cjs` is API-only (no browser) and asserts: inherited and explicit zones, unknown zone 422, the revision rules (422 without `expected_updated_at`, 409 when stale, pending `next_run_at` untouched), legacy records reading `Asia/Kolkata`, calendar `next_run_at` equal to a wall-clock instant computed independently in JavaScript with `Intl` (New York and Kolkata), UTC `Z` instants, and the native worker dispatching a 60-second interval schedule exactly once (the harness worker polls every 5 seconds via `WEAVES_SCHEDULE_POLL_SECONDS`). The running stack cannot inject time, so the calendar target is a wall-clock time ten minutes ahead.

## TW-01 public waitlist (API only)

`waitlist_checks.py` runs in the seed container after the native worker is up and records `waitlist` in the private fixture file; `controls.spec.cjs` asserts each named result. No browser and no cookie is used: every call goes to `/api/v0/waitlist` as the website's relative URL would, each synthetic visitor from its own `X-Forwarded-For` source. It joins with a company address, answers a single choice and a multiple choice with other text, changes and clears an answer, resumes with the private `X-Waitlist-Token` header only, and joins again with the same address in capitals from another source: the response has the identical shape, a new token and no answer, and the first token still holds its answers. Bad tokens return one generic 401, a bad address 422, and the eleventh join from one source 429 with `Retry-After`; no response sets a cookie and no account or session exists for the address (`operator_bearer` finds none). A further visitor checks the Other rule of question set 2: `role` and `company_location` (like `waiting_on` and `tools`) ask what Other is, a bare or blank Other, or text over 60 characters, is a 422 that stores nothing, the trimmed text resumes, and the operator list, CSV (`<question>_other` columns) and stats (`other_texts`) show it; that entry is then erased. The real `infra/gcp/singlevm/waitlist.py` (mounted at `/suite/operator/waitlist.py`, owner connection) then lists, exports and reports the rows, they are checked directly in PostgreSQL (global rows, token stored only as a digest, two submissions on one entry), `set-status` is audited with `actor_kind` operator, and `delete --email` erases the entry and both submissions so the token stops working.

## T5-I01 tenant limits and atomic admission

`phase5/limits_checks.py` runs in two phases (the host pauses the native worker only for the first so the queue cannot drain mid-burst) and records `limits` in the private fixture file. The stack runs with `WEAVES_LIMITS_MODE=enforce`. A fresh organization gets a queue cap of 3 from the real operator script `organization_limits.py` (mounted at `/suite/operator/organization_limits.py`, owner connection), then twelve simultaneous task creations race at the cap: exactly three are admitted and nine get `429` `limit_exceeded` with `Retry-After` and only the caller's own `{resource, limit, used}`. ## T5-I03 usage ledger (API only)

`phase5/usage_checks.py` runs in two stages around a worker kill, orchestrated by `run.py` (only the runner may touch the Compose project). `start` creates tasks through the real API and the independent native worker; the fake model reports 10 input and 10 output tokens for every call. It then checks that every succeeded agent run has exactly one `settled` ledger row with identical tokens, that `usage_daily` equals the ledger, that `GET /api/v0/usage` returns each organization only its own numbers (a member gets 403, an undeclared query parameter or a range over 92 days 422), that the restricted `weaves_app` role bound to one tenant (or to none) cannot read another tenant's `usage_ledger` or `usage_daily`, that a replayed reserve and a replayed settle with different tokens change nothing, and that the real `infra/gcp/singlevm/usage_report.py` (mounted at `/suite/operator/usage_report.py`, owner connection) reports the same per-organization totals and no content. It then queues a workflow-trigger job whose prompt contains `HOLD-FOR-USAGE-CRASH`; the fake provider holds that model call open for 100 s, leaving a `reserved` row. The runner SIGKILLs the worker and starts a new one; `finish` waits for the job lease fence (120 s) and the reconciler tick and asserts the row became `unknown` (`lease_expired`) exactly once, that no tokens were counted for it, and that both the API and the operator report show it as an unknown call. This control adds about three minutes to a full run.

## T6-I03 kill switches and tenant quarantine (API only)

`phase6/controls_checks.py` runs in the seed container after the usage control, against the running API and independent worker (neither is restarted). It drives the real `infra/gcp/singlevm/organization_lifecycle.py` and `platform_control.py` (mounted under `/suite/operator`, owner connection). Tenant A gets a schedule and a webhook trigger; `quarantine` then refuses A's API calls, new tasks and webhook, disables the schedule and trigger in the database and creates no job, while tenant B still serves and completes a task in the worker and its rows are byte-identical; a repeated quarantine is idempotent. `release-quarantine` restores A, re-enables exactly the disabled schedule and trigger and the webhook accepts again; B is unchanged. The control adds about one minute to a full run.
